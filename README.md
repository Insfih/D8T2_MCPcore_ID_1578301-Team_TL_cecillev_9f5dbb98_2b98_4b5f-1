## Введение

>В Лавке «Школы 21» мерч покупают за коины. Сейчас участник вручную проверяет остатки, баланс и возможность получить заказ. На следующем проекте к Лавке подключат программного помощника. Подготовьте инструменты, которыми он сможет пользоваться.
Помощник может указать неверный размер, повторить запрос или попытаться отменить уже выданный заказ. Сервер должен проверить каждый запрос и либо выполнить действие, либо объяснить отказ. После неудачной покупки баланс и остатки должны остаться прежними.

**Вопрос: как дать другой программе доступ к действиям Лавки и сохранить её правила?**

Вы уже работали с Python и SQL. Теперь код нужно разделить между участниками и собрать в одну работающую систему. Один инструмент уже готов `get_product`: по нему можно проследить весь путь запроса от `src/mcp_adapter.py` через `src/read_handlers.py` к `src/storage.py`.

**Что вы собираете:**

MCP — протокол, по которому программа узнаёт, какие инструменты предоставляет сервер, и вызывает их с нужными аргументами. Инструмент здесь — операция, например `get_product`. Клиент отправляет запрос, сервер возвращает результат. В этом проекте клиентом служит готовая программа в терминале. 

У сервера семь инструментов:

| Инструмент | Что делает |
|------------|------------|
| `list_products` | Показывает каталог и остатки |
| `get_product` | Показывает один товар |
| `get_coin_balance` | Показывает баланс участника |
| `create_order` | Создаёт заказ, списывает коины и резервирует товар |
| `get_order_status` | Показывает состояние заказа |
| `cancel_order` | Отменяет заказ и возвращает товар и коины |
| `confirm_pickup` | Отмечает, что заказ выдан |

Поля запросов, ответы и правила перечислены в правилах Лавки (`materials/lavka_rules.md`).

## Рекомендации к проекту

**Обрати внимание:**

- `materials/lavka_rules.md` — правила Лавки: данные, ответы, контракты, покупка, состояния заказа
- `materials/team.md` — как распределить работу на четверых
- `materials/architecture.md` — как устроен сервер и путь готового вызова
- `materials/testing.md` — как проверять сервер и как запускать общую проверку
- `materials/acceptance.md` — критерии проверки
- `contracts/tools_schemas.json` — схемы семи инструментов
- `docs/` — шаблоны трёх документов команды: `team.md`, `system.md`, `change.md`
- `RUN.md` — инструкция запуска
- `src/` — код сервера
- `testing/` — ваши тесты
- `checks/` — общие проверки
- `client.py` — клиент

Выполняйте задания в одном командном репозитории. Выберите лида и распределите четыре участка работы по инструкции для команды (`materials/team.md`).\
Используйте установленный на рабочем месте `python3` и подготовленные для проекта зависимости.

```bash
python3 check_environment.py
python3 client.py demo
```

Первая команда проверяет необходимые модули и сообщает об обнаруженной проблеме. Вторая сама запускает сервер, запрашивает товар и показывает ответ. 

**Материалы для выполнения:**

| Где | Что лежит | Что с этим делать |
|-----|-----------|-------------------|
| `src/` | Работающий `get_product`, подключение к базе и заготовки функций | Дописать отмеченные части |
| `client.py` | Клиент для демонстрации и ручных запросов | Использовать для запуска и проверки |
| `data/seed.sql` | Учебные товары, пользователи и таблицы | Сохранить исходные записи |
| `contracts/tools_schemas.json` | Схемы семи инструментов | Заполнить описания |
| `testing/` | Пример теста | Добавить тесты своих решений |
| `checks/` | Общие проверки приёмки | Запускать без редактирования |
| `docs/`, `RUN.md` | Шаблоны трёх коротких документов и запуска | Заполнить по ходу работы |

**Как работать с проектом:**

- Перед выполнением проект необходимо склонировать с GitLab в одноименный репозиторий. Проект групповой: команда работает в одном командном репозитории.
- Все файлы с кодом необходимо создавать в папке `src/`.
- После клонирования необходимо создать ветку `develop` и вести разработку в ней. 
- Все результаты обязательной части сохраняй в склонированном репозитории: код — в `src/`, тесты — в `testing/`, описания инструментов — в `contracts/tools_schemas.json`, документы — в `docs/` и `RUN.md`, журнал прогона — в `logs/client.jsonl`. Локальные базы `data/*.db` и виртуальное окружение в репозиторий не добавляй.
- Сервер, тесты и общая проверка должны запускаться локально на подготовленном рабочем месте. Доступ к платным сервисам, ключам к моделям и внешнему ИИ для выполнения и проверки не требуется.
- На проверке лид одной команды проверяет лида другой. Остальные участники могут присутствовать и задавать вопросы.
- Оценка общая для команды. Личный вклад, количество коммитов и распределение строк кода не измеряются. Команда отвечает за предъявленную версию и её объяснение.
- На проверке нужно запустить сданный код, показать обычный запрос и отказ, разобрать путь одного вызова и рассказать о конверте. Писать новый код под таймером не требуется. Порядок и критерии открыты заранее в правилах приёмки (`materials/acceptance.md`).

**Как работать с ИИ:**

Используйте доступные на площадке бесплатные ИИ-сервисы. Можно просить объяснения, генерировать код и тесты, разбирать ошибки и сравнивать варианты. Обсуждайте решения, которые затрагивают чужой участок, с командой.\
Проверяйте предложенный код на данных Лавки. Если модель утверждает, что повторная отмена безопасна, покажите это запросом и состоянием базы. 

## День 08

### Задание 1. Увидеть работающий инструмент

**Результат: каждый в команде видел реальный ответ сервера; в `docs/team.md` записано распределение работы.**

1. Запустите демонстрацию. Она найдёт худи, затем запросит несуществующий товар. Первый запрос вернёт данные, второй — понятную ошибку.
2. Откройте `src/mcp_adapter.py`, `src/read_handlers.py` и `src/storage.py`. Найдите функцию, которая принимает запрос, место чтения из SQLite и место формирования ответа.
3. Вместе проследите путь `get_product` по коду. В `docs/system.md` запишите его одной строкой с именами функций.

Читать весь проект до первого запуска не нужно. Короткая справка — как устроен сервер (`materials/architecture.md`).

### Задание 2. Договориться об инструментах

**Результат: `contracts/tools_schemas.json` содержит семь описаний, по которым можно выбрать нужный инструмент.**

Каркас контрактов уже дан. Контракт — договор о том, что инструмент принимает и возвращает. Поля и типы в нём соответствуют правилам Лавки.\
1. Для шести незавершённых инструментов замените пометку `TODO` собственными описаниями. Укажите, когда нужен инструмент, что он меняет и в каком случае откажет. Например, описание отмены должно предупреждать, что выданный заказ отменить нельзя.
2. Проверьте описания внутри команды: один человек называет ситуацию, другой выбирает инструмент по описанию. Уточните текст, если выбор оказался неоднозначным.
3. В `docs/system.md` заполните границы системы: какие действия она выполняет и чего клиенту обещать нельзя. Шаблон уже лежит в файле.

### Задание 3. Собрать первый заказ

**Результат: работают 4 инструмента чтения и `create_order`; заказ виден в базе, баланс и остаток изменились правильно; в `testing/` есть собственные тесты расчёта и отказа.**

1. Разойдитесь по участкам из `docs/team.md`. Доведите чтение каталога, баланса и состояния заказа. Реализуйте расчёт стоимости, проверку доступности покупки и запись заказа.\
Правила расчёта находятся в `src/domain.py`, SQL — в `src/storage.py`, последовательность действий — в обработчиках. Подключение к базе и регистрация инструментов уже подготовлены. Функции, которые вам нужно закончить, отмечены `TODO` и пока вызывают `NotImplementedError`.\
Участки готовы не одновременно, и это нормально. Правила в `src/domain.py` не обращаются к базе: их можно закончить и покрыть тестами, пока хранение не готово. Обработчик покупки пишите вместо временной заглушки хранения — словаря с теми же полями, о которых вы договорились. Заглушка живёт только в тесте: сдавать её вместо SQL нельзя.
2. Для проверки оформите одну бутылку для `student_01`: цена — 150 койнов, баланс станет 850, остаток — 11. Затем попробуйте купить худи от имени `student_poor`. Сервер должен отказать и сохранить прежние данные.
3. Добавьте собственные тесты. Готовый пример показывает устройство теста, но в счёт не идёт. К приёмке ваших тестов должно быть не меньше трёх: расчёт стоимости; отказ, после которого данные не изменились; повторное действие с заказом.

Перед уходом соедините работу в общей ветке `develop`. Каждый покажет команде свой участок на одном запросе. Если первый заказ ещё не проходит, запишите конкретную причину и начните второй день с неё.

## День 09

### Задание 4. Довести заказ до конца и проверить отказы

**Результат: работают все 7 инструментов; повторные и ошибочные действия не портят данные.**

1. Доделайте отмену и выдачу. У заказа три состояния: `created`, `cancelled`, `picked_up`. Отменять и выдавать можно только заказ в состоянии `created`.
2. Проверьте полный путь: создать заказ, узнать состояние, отменить; создать другой, выдать, попытаться отменить выданный. Убедитесь, что повторная отмена не возвращает коины ещё раз.

```bash
python3 client.py scenario
python3 -m pytest -q
python3 checks/acceptance.py --project . --profile base
```

Если проверка падает, начните с первого сообщения об ошибке. Исправляйте поведение сервера; готовые проверки и исходные товары менять нельзя.

### Задание 5. Открыть конверт

**Результат: в `docs/change.md` записано полученное условие, предпринятое изменение и результат проверки.**

Когда базовые проверки начнут проходиться без ошибок, вскройте конверт. В нём — новое условие от Лавки.\
До изменения кода запишите, какие файлы, по вашему мнению, придётся тронуть. Затем внесите изменение и добавьте тест, который отличает новое поведение от старого. После этого запустите весь набор проверок с профилем своего конверта.\
Задача — разобраться с новым условием и сохранить работающий сервер.\
Если за 45 минут не получилось, зафиксируйте, где остановились. Можно продолжить до общей сдачи или вернуться к базовому варианту. В файле укажите, что именно сдаёте: `base` или номер конверта. Незавершённый конверт не отменяет зачёт основной части. Выполненное изменение отмечается отдельным дополнительным пунктом.

### Задание 6. Передать сервер следующему разработчику

**Результат: другой человек запускает сервер по `RUN.md` и понимает его возможности по `docs/system.md`.**

1. Заполните `RUN.md`: команды запуска и проверки, пример запроса, способ начать с чистой учебной базы и профиль сдаваемой версии. Укажите, какие файлы сохраняют состояние.
2. Доведите `docs/system.md`: путь запроса, границы системы и один пример отказа с объяснением, где он проверяется. Приложите журнал одного полного прогона клиента, созданный программой.
3. Поменяйтесь внутри команды: участник, который не писал инструкцию, выполняет её на доступном рабочем месте с подготовленным окружением. Исправьте места, где понадобились устные подсказки.
4. Сохраните результат в репозитории. На десятом дне понадобятся код сервера, контракты, паспорт системы и инструкция запуска.
